===== STORY =====

𝟰𝟱 𝗙𝗿𝗲𝗲 𝗔𝗴𝗲𝗻𝘁 𝗦𝗸𝗶𝗹𝗹𝘀 𝗙𝗼𝗿 𝗦𝗵𝗶𝗽𝗽𝗶𝗻𝗴 𝗔 𝗦𝗮𝗮𝗦, 𝗡𝗼𝘁 𝗝𝘂𝘀𝘁 𝗪𝗿𝗶𝘁𝗶𝗻𝗴 𝗖𝗼𝗱𝗲

You ask a coding agent to build a feature. It writes the code, runs the tests, and tells you it all looks good.

𝗧𝗵𝗲 𝘀𝗮𝗺𝗲 𝘀𝗲𝘀𝘀𝗶𝗼𝗻 𝘁𝗵𝗮𝘁 𝘄𝗿𝗼𝘁𝗲 𝘁𝗵𝗲 𝗰𝗼𝗱𝗲 𝗷𝘂𝘀𝘁 𝗮𝗽𝗽𝗿𝗼𝘃𝗲𝗱 𝗶𝘁.

Paweł Huryn's new open-source repo, product-engineering, is built around stopping that. It's 45 agent skills in six packs, MIT-licensed, at 𝟲𝟯𝟳 𝘀𝘁𝗮𝗿𝘀 today.

The rule at the centre is simple. Before every push that deploys, a fresh reviewer that never saw the build reads the change. By default that's the first one installed of Codex, Claude Code and Grok, started read-only, with no MCP servers and memory off.

It loops. Another round, then another, until one finds nothing the change introduced above Low and nothing High or Critical of any age. The README puts it in one line: "𝘛𝘩𝘦 𝘴𝘦𝘴𝘴𝘪𝘰𝘯 𝘵𝘩𝘢𝘵 𝘸𝘳𝘰𝘵𝘦 𝘵𝘩𝘦 𝘤𝘰𝘥𝘦 𝘯𝘦𝘷𝘦𝘳 𝘤𝘭𝘦𝘢𝘳𝘴 𝘪𝘵."

The rest follows the path from idea to paying users:

• 𝗽𝗿𝗼𝗱𝘂𝗰𝘁 (𝟴): research the alternatives, pick a segment, write one proposal with screens
• 𝗮𝗶-𝘀𝗵𝗶𝗽𝗽𝗶𝗻𝗴 (𝟭𝟭): reviews, a release gate, static security and performance checks
• 𝗮𝗴𝗲𝗻𝘁-𝘁𝗲𝗮𝗺𝘀 (𝟱): one agent coordinates, another builds
• 𝗮𝗴𝗲𝗻𝘁-𝗵𝗮𝗿𝗻𝗲𝘀𝘀 (𝟲): handovers, retros, guardrail hooks
• 𝗮𝗽𝗽-𝘀𝘁𝗮𝗰𝗸 (𝟭𝟰): auth, billing, email, legal pages, analytics, monitoring
• 𝘄𝗼𝗿𝗸-𝗵𝘂𝗺𝗮𝗻𝗶𝘇𝗲𝗿 (𝟭)

If you're a PM or a solo founder, it's aimed at you. You don't read code line by line. You approve a proposal, click through the flows (it budgets 𝟭𝟱 𝘁𝗼 𝟮𝟬 𝗺𝗶𝗻𝘂𝘁𝗲𝘀 for a mid-size app) and say go at release. "𝘚𝘪𝘭𝘦𝘯𝘤𝘦 𝘪𝘴 𝘯𝘰𝘵 𝘨𝘰."

If you build, look at how the rules are kept. Each one carries a dated receipt of what broke or what was measured, 𝗮𝗯𝗼𝘂𝘁 𝟳𝟬𝟬 𝗼𝗳 𝘁𝗵𝗲𝗺, from three of his live products: AskOne, Staygreen and AFK Pilot.

It isn't the first big skill collection. Superpowers covers brainstorm, plan, TDD and review. gstack has role skills, a Codex second opinion and a deploy command. This one leans further into production: billing, legal pages, monitoring.

Some caveats. 𝗧𝗵𝗲 𝗮𝗽𝗽-𝘀𝘁𝗮𝗰𝗸 𝗽𝗮𝗰𝗸 𝗮𝘀𝘀𝘂𝗺𝗲𝘀 𝗡𝗲𝘅𝘁.𝗷𝘀, 𝗦𝘂𝗽𝗮𝗯𝗮𝘀𝗲, 𝗖𝗹𝗲𝗿𝗸 𝗮𝗻𝗱 𝗡𝗲𝘁𝗹𝗶𝗳𝘆. The README says the evidence varies: 28 skills come from real products, 14 are established methods, one rests on a single day of CLI runs. The gemini-agents skill carries Google's own warning that it isn't supported on consumer plans and can lead to suspension. And the 41 auto-loading skills cost 𝗮𝗯𝗼𝘂𝘁 𝟮,𝟳𝟬𝟬 𝘁𝗼𝗸𝗲𝗻𝘀 𝗮 𝘁𝘂𝗿𝗻 in Claude Code.

Was reading through Paweł Huryn's product-engineering repo today. On the surface it's 45 agent skills in six packs, MIT, works with Claude Code, Codex, Cursor, Gemini CLI and others.

𝗧𝗵𝗲 𝘀𝗸𝗶𝗹𝗹𝘀 𝗮𝗿𝗲𝗻'𝘁 𝘁𝗵𝗲 𝗶𝗻𝘁𝗲𝗿𝗲𝘀𝘁𝗶𝗻𝗴 𝗽𝗮𝗿𝘁 𝗶𝗺𝗼. 𝗧𝗵𝗲 𝘀𝘁𝗼𝗽𝗽𝗶𝗻𝗴 𝗿𝘂𝗹𝗲 𝗶𝘀.

When one agent writes code and then reviews it, the reviewer shares the writer's context. Same assumptions, same blind spots. It's a bit like proofreading your own essay right after writing it. You read what you meant, not what's on the page.

So the repo forces a fresh reviewer: a new session that never saw the build. Read-only, no MCP servers, memory off. By default it picks the first installed of Codex, Claude Code and Grok.

Then it doesn't stop after one pass. Rounds continue until one finds 𝗻𝗼𝘁𝗵𝗶𝗻𝗴 𝘁𝗵𝗲 𝗰𝗵𝗮𝗻𝗴𝗲 𝗶𝗻𝘁𝗿𝗼𝗱𝘂𝗰𝗲𝗱 𝗮𝗯𝗼𝘃𝗲 𝗟𝗼𝘄 𝗮𝗻𝗱 𝗻𝗼𝘁𝗵𝗶𝗻𝗴 𝗛𝗶𝗴𝗵 𝗼𝗿 𝗖𝗿𝗶𝘁𝗶𝗰𝗮𝗹 𝗼𝗳 𝗮𝗻𝘆 𝗮𝗴𝗲. That's a convergence criterion, not a checkbox, which I think is the right shape for it.

The other thing I liked is the bookkeeping. Rules carry a receipt, a date and what broke, 𝗮𝗯𝗼𝘂𝘁 𝟳𝟬𝟬 𝗼𝗳 𝘁𝗵𝗲𝗺, collected while shipping three products. And when the skill descriptions got too heavy, the author measured it: 𝟵,𝟭𝟰𝟯 𝘁𝗼𝗸𝗲𝗻𝘀 𝗮 𝘁𝘂𝗿𝗻 𝗱𝗼𝘄𝗻 𝘁𝗼 𝟮,𝟰𝟮𝟯 after a rewrite (it's about 2,700 now with 41 auto-loading skills).

What I'd hold loosely: there are no published numbers on how many bugs the fresh-reviewer loop actually catches versus a single review. The README is upfront that evidence varies by skill, and the app stack is opinionated (Next.js, Supabase, Clerk, Netlify).

If you adopt it, measure it on your own repo:

1. Plant 10 to 20 bugs you know about in a branch.
2. Run one normal review as the baseline. Count what it finds.
3. Run the independent-review loop to convergence. Count again, and log tokens and wall time.
4. Read the reviewer transcripts. Look at what it flagged that wasn't real, not only what it caught.

===== ETHAN MOLLICK STYLE =====

𝗜𝗳 𝗡𝗼𝗯𝗼𝗱𝘆 𝗥𝗲𝗮𝗱𝘀 𝗧𝗵𝗲 𝗖𝗼𝗱𝗲, 𝗪𝗵𝗼 𝗖𝗵𝗲𝗰𝗸𝘀 𝗜𝘁?

More people are building real software without reading the code: product managers, founders, designers. That raises an odd question. When an AI writes the app, who gets to say it's ready?

Paweł Huryn, who writes The Product Compass newsletter, just released one answer as a free toolkit. It's called product-engineering: 𝟰𝟱 "𝘀𝗸𝗶𝗹𝗹𝘀", which are written instructions that coding agents like Claude Code and Codex load when a task matches.

𝗧𝗵𝗲 𝗺𝗮𝗶𝗻 𝗶𝗱𝗲𝗮 𝗶𝘀 𝗯𝗼𝗿𝗿𝗼𝘄𝗲𝗱 𝗳𝗿𝗼𝗺 𝗵𝗼𝘄 𝗽𝗲𝗼𝗽𝗹𝗲 𝘄𝗼𝗿𝗸. You don't let someone mark their own exam. So the agent that built the feature never approves it. A second, fresh agent reviews it, and it can run on a different company's model. Then again, until a round finds nothing serious.

The human still has a job. You approve the plan, click through the app for 15 or 20 minutes, and give a clear "go" before release. The README is blunt about it: "𝘚𝘪𝘭𝘦𝘯𝘤𝘦 𝘪𝘴 𝘯𝘰𝘵 𝘨𝘰."

There's evidence on both sides. For: the author built three live products this way (a Q&A tool, a monitoring service and a remote control for coding agents), and logged about 700 rules, each with a date and what went wrong.

Against: these are one builder's results. The repo publishes no figures on how many bugs the review loop catches. Its own notes say some skills rest on thin evidence, and the setup assumes a specific set of web tools.

So what we know is that a careful person found a working method. What we don't know yet is how well it travels to other teams and other products.
