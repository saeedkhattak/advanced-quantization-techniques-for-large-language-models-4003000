===== 1. STORY =====

The Missing Piece In AI Software Factories Isn't The Coding Agent

Picture the pipeline a lot of teams are building. A ticket comes in. An agent plans the work, another writes the code, another reviews it, and a PR opens. No human in the middle.

Now give it a real ticket at a big company: let customers pay with a gift card.

That one change touches payments, pricing, orders and the receipt email. Four repos, maybe more, owned by four teams. Which ones should the agents open?

Today a person answers that. They pick the repos, load them into a workspace and hope they didn't miss one. A factory can't stop and wait for that person on every ticket.

AWS Labs open-sourced CodeKB to be the part of the pipeline that answers it. It's two weeks old, Apache-2.0, and v1.1.0 shipped on 27 November. The README frames it exactly this way: "Code understanding for the world of autonomous software factories."

Here's how it builds that understanding.

It clones each repo and parses every function and class with Tree-sitter (14 languages). It rebuilds the call graph. Then a Claude model on Amazon Bedrock writes a business description of every function, including what the functions it calls do. Those descriptions are embedded as vectors.

So an agent can ask over MCP, "where are payments authorized?", with no repo named at all. If it gives no scope, the search runs across every analyzed repo and returns matching functions, each tagged with the repo it lives in. From there the agent follows callers and callees to see what the change will hit.

When code changes, a refresh re-summarizes only the changed functions and the callers that described them. That matters when agents are merging all day.

And it all runs inside your own AWS account.

It isn't a finished factory part yet. Bedrock is required even on a laptop, and every function costs an LLM call (default model Claude Opus 4.6). Scheduled refresh, resuming after a restart, scaling MCP across containers and detecting which repos depend on each other are all still on the roadmap. There are no published benchmarks.

Sourcegraph and Augment already serve cross-repo context over MCP too, so the category isn't new. What's new is a big cloud vendor saying the quiet part: in an agent-run pipeline, the scarce thing is knowing where to look.

===== 2. KARPATHY STYLE =====

Reading the CodeKB README from AWS Labs. The framing is "autonomous software factories", and I think the framing is the most useful part.

If you sketch a factory as a loop (ticket in, plan, code, review, PR out), the obvious bottleneck looks like the model writing code. It mostly isn't anymore. The step that quietly still needs a human is the first one: deciding which parts of a large codebase the task touches. In a big company that knowledge is spread across hundreds of repos and a few people's heads.

CodeKB tries to turn that knowledge into something an agent can query.

The mechanism is simple and a bit clever. Parse every function, rebuild the call graph, then have an LLM write a business-language description of each function that includes what its callees do. Embed the descriptions, not the code.

The analogy I'd use is a new hire's first week. You don't hand them the source. You walk them through what each part of the system is for. CodeKB writes that walkthrough once, for every function, and keeps it updated: a refresh re-summarizes only the changed functions and the callers whose descriptions mentioned them.

Over MCP, an agent can search those descriptions with no scope and get hits from every analyzed repo, then follow the call graph from there. That's the factory's "which repos?" question answered by a tool call instead of a person.

It's early. Bedrock is required even locally, every function costs an LLM pass, and the operational bits a factory needs (scheduled refresh, resumable jobs, scale-out MCP) are on the roadmap. No benchmarks yet.

What I'd want to see: a fixed set of past tickets, agents run with and without it, scored on whether they found the repos a senior engineer would have named. If that number is high, this layer becomes table stakes.

===== 3. SIMON WILLISON STYLE =====

CodeKB, new from AWS Labs (Apache-2.0, v1.1.0 released 27 November 2026).

The README opens with: "Code understanding for the world of autonomous software factories." And then: "An autonomous software factory cannot wait for a human to hand-pick repositories for every task."

That's the pitch. Agents need to find the relevant repos themselves.

What it is: one container serving a web UI, a REST API and an MCP server. It parses code with Tree-sitter, rebuilds the call graph, and has an LLM on Amazon Bedrock describe each function "in business language, together with the code it calls". Titan embeds the descriptions into Amazon S3 Vectors.

The detail that makes the factory claim real is in the MCP tool's own docstring. get_component_from_description takes an optional space_id, space_ids or hyperspace_id, and the docstring says "omit all to search across every space". So an agent can describe a task and get matches from every analyzed repo, each with a space-qualified ID it can pass to show_component, trace_flow or show_dependencies.

The other piece is incremental refresh, which "walks the call graph in reverse to find the callers whose descriptions included the changed code" and re-summarizes only those.

Things to be careful about:

• It needs Amazon Bedrock even when run locally. Default model: Claude Opus 4.6.
• Cost is mostly Bedrock summarization and grows with the number of functions.
• The CDK deployment's default non-dev stages run 10 Fargate tasks of 4 vCPU and 16 GB each.
• A space is one branch at one commit, capped at 10,000 source files.
• Several things a factory would lean on are roadmap items: scale-out MCP (Now), scheduled refresh and resumable analysis (Next), IAM SigV4 machine-to-machine auth (Exploring), and automatically finding which repos depend on each other (Later).
• No benchmarks yet; benchmarking is listed under "Next".

Start with docs/mcp.md, then ROADMAP.md.

===== 4. SWYX STYLE =====

Every serious "AI software factory" pitch eventually hits the same wall: the agents can write code, but nothing tells them which of your hundreds of repos the ticket is about.

That missing layer is turning into its own category, a context engine that agents query before they act. AWS just shipped an open-source one, and it's explicitly built for the factory case.

Who's already in the category:

• Sourcegraph: cross-repo search and precise code navigation over MCP.
• Augment Context Engine: shipped as a standalone MCP server in February 2026.
• DeepWiki: generated wikis and Q&A for public GitHub repos.
• Greptile: a code graph, mostly in service of AI code review.
• AWS's own earlier Git Repo Research MCP server: per-repo semantic search, now deprecated.

CodeKB (awslabs, Apache-2.0) indexes descriptions rather than code. Claude on Bedrock writes a business summary of every function, covering what its callees do. An agent searches those by intent across every analyzed repo in one MCP call, then walks the call graph for impact. Refresh only redoes what changed. All of it sits in your own AWS account.

That last point is the AWS play. If agents are going to run unattended on your code, enterprises will want the map of that code inside their own account, not a startup's cloud.

It's two weeks old. Bedrock is required even locally, there are no benchmarks, and the ops features a factory needs (scheduled refresh, resumable jobs, scale-out MCP) are still roadmap.

My read: the coding model is becoming a commodity, and the factory's moat moves to who owns the map of your codebase. Every cloud will ship one of these within a year, and they'll end up competing on refresh cost and retrieval benchmarks nobody has published yet.

===== 5. HAMEL HUSAIN STYLE =====

AWS Labs pitches CodeKB as the code-understanding layer for "autonomous software factories". If you're building an agent pipeline, here's how I'd think about it.

In a factory, this sits at the very start. Before any agent plans or writes, it asks CodeKB which code the ticket touches. Every later step trusts that answer. Which makes it the step you most need to measure.

What it gives you:

• A business-language description of every function, written by Claude on Bedrock, including what its callees do.
• An MCP search tool that, with no scope given, searches every analyzed repo and returns matches tagged with their repo.
• Call-graph tools (show_dependencies, trace_flow) for impact analysis.
• Incremental refresh that redoes only changed functions and their callers.

What it doesn't give you:

• Evidence. No published benchmarks; benchmarking is on the roadmap under "Next".
• Factory-grade ops yet. Scheduled refresh and resumable analysis are "Next", scale-out MCP is "Now".
• Free runs. Every function costs an LLM call, and Bedrock is required even locally.

The failure mode to watch: the summaries are LLM output. A wrong summary at step one sends every agent downstream to the wrong repo, and nothing after it will notice.

Before trusting it in a pipeline:

1. Pull 30 to 50 closed tickets where you know exactly which repos and functions changed.
2. Run only the retrieval step, with no scope, and score recall of the right repos and call sites.
3. Compare against your current approach, whether that's grep, embeddings over raw code, or a human picking.
4. Track Bedrock token cost per space (CodeKB shows it after each analysis).
5. Read every miss and label it: bad summary, bad search, or a dependency between repos it couldn't see.

Ship it into the factory only if step 2 beats step 3.

===== 6. ETHAN MOLLICK STYLE =====

Companies are starting to build what AWS calls "autonomous software factories": chains of AI agents that take a request, write the code and submit it, with no person in between. What stops them from working?

Often it isn't the AI's coding skill. It's that it doesn't know the company.

Big organizations split their software into hundreds of separate projects. One feature, like checkout on a shopping site, can be spread across the cart, pricing, payments, orders and email, each owned by a different team. Knowing which pieces a change will touch usually lives in a few experienced engineers' heads. Today a human picks the right projects for the AI. A factory can't stop and ask every time.

AWS Labs just released a free, open-source tool called CodeKB aimed at that gap. It reads every function across all of a company's code and has an AI write a plain-English note about what each one does for the business, including what it gets done through the other code it calls.

The agents can then ask it questions like "where do we take payments?" and get pointed to the right places across all the projects at once, before they start changing anything.

Think of it as writing down the tour a senior engineer gives a new hire, for every corner of the system, and keeping it updated as the code changes.

There are real reasons for caution. Nobody has published evidence yet that it makes the agents' work better. The notes are themselves AI-written, so they can be wrong, and in a pipeline with no human, a wrong note can send every later step in the wrong direction. Some features an unattended system would need are still on the roadmap.

But the direction says something. If the hard part of automating software is knowing the organization, then the valuable thing isn't the AI that writes the code. It's whoever writes down how the company actually works.

What happens to the role of the senior engineer when that knowledge becomes a service the agents call?
