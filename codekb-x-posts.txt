===== 1. STORY =====

Everyone Is Building A Software Factory. Who Tells The Agents Where The Code Lives?

"Software factory" is suddenly everywhere.

Factory published "Factory 2.0: From coding agents to software factories" in June. Warp launched Warp Factories in August. Coforge announced an Autonomous Software Factory in October. Qodo is shipping approval workflows for agent-built PRs and writes about the software factory on its blog.

YouTube has caught up too, with videos like Gauntlet's "How to Build Your Own Software Factory".

And open source is full of them: superplane, Fabro ("the open source dark software factory"), and Addy Osmani's factory, "a reference software factory for Claude Code and Codex".

Getting a pipeline of agents to plan, code, review and open a PR is the part people have figured out. The harder part is context. The agents don't know your company.

Take one ticket at a big shop: let customers pay with a gift card.

That touches payments, pricing, orders and the receipt email. Four repos, maybe more, owned by four teams.

Normally an engineer who knows the system pulls those repos into a workspace and points the agent at them. But in an autonomous factory there's no engineer at that step. The agent gets the ticket and has to decide for itself which of hundreds of repos matter. It can't ask anyone.

AWS Labs open-sourced CodeKB for exactly this step. Its README says it plainly: "An autonomous software factory cannot wait for a human to hand-pick repositories for every task."

How it works:

It parses every function in every repo with Tree-sitter and rebuilds the call graph. Then a Claude model on Amazon Bedrock writes a business description of each function, including what the code it calls does. A Bedrock Guardrail masks secrets and PII first. The descriptions become vectors.

Now an agent can ask, over MCP, "where are payments authorized?" without naming a repo. With no scope given, the search covers every analyzed repo. From each hit it can walk callers and callees to see what the change will break.

When code changes, only the changed functions and the callers that described them get re-summarized.

Now the caveats.

It needs an LLM, and specifically Claude on Amazon Bedrock (default Claude Opus 4.6). Embeddings are fixed to Amazon Titan. No OpenAI, no Ollama.

You can run the app locally in Docker, but you still need an AWS account. The setup script creates S3 buckets, a vector index, a KMS key and a Guardrail there. Local mode is for one person with no sign-in. For a team, you deploy it into AWS with CDK.

Every function costs an LLM call. There are no published benchmarks yet, and scheduled refresh and resumable jobs are still on the roadmap.

Factories are easy to build now. Giving them the knowledge your senior engineers carry is the real work.

===== 2. KARPATHY STYLE =====

Thinking about the "software factory" wave for a moment.

The phrase is everywhere right now. Factory frames its 2.0 release as "from coding agents to software factories". Warp sells Warp Factories, Coforge an Autonomous Software Factory, and Qodo writes about quality control for the agentic software factory. There's a steady stream of how-to videos (Gauntlet has a full class on it), and open-source versions like superplane, Fabro and addyosmani/factory.

The loop itself is not that hard anymore: ticket in, plan, code, review, PR out. I think the interesting problem is the very first step, the one that still quietly assumes a human.

In a big company, a single feature like checkout is spread across many repos. Someone who knows the system pulls the right ones into a workspace before the agent starts. That someone is doing retrieval, from memory. Take them out of the loop and the agent is starting cold, with hundreds of repos and no idea which matter.

AWS Labs' CodeKB is an attempt to make that memory queryable.

The trick is in what gets embedded. It parses every function, rebuilds the call graph, then has an LLM write a business-language description of each function that includes what its callees do. You embed those descriptions, not raw code. You end up searching explanations, built bottom-up along the call graph.

Over MCP, an agent searches with no scope and gets hits across every analyzed repo, then walks callers and callees. On a code change, only the changed functions and the callers that mentioned them get re-summarized.

The practical constraints are worth being clear about. The LLM has to be Claude on Amazon Bedrock, and embeddings are Titan. You can run the container on your laptop, but it still needs an AWS account for the models, the vector index, S3 and KMS. Team use means deploying it into AWS. Every function is an LLM call, and there are no benchmarks yet.

What I'd want to see: a set of past tickets, an agent run with and without this, scored on whether it found the repos a senior engineer would have picked.

===== 3. SIMON WILLISON STYLE =====

Notes on software factories, and on the AWS tool aimed at their weakest step.

The term is everywhere this year:

• Factory: "Factory 2.0: From coding agents to software factories" (15 June 2026).
• Warp: "Introducing Warp Factories", open infrastructure for building your software factory (August 2026).
• Coforge: "Autonomous Software Factory" press release (29 October 2026).
• Qodo: Auto Approval Workflows and Agent Session Review, framed around the software factory (November 2026).
• Video: Gauntlet Night School, "How to Build Your Own Software Factory".
• Open source: superplanehq/superplane, fabro-sh/fabro, addyosmani/factory, the-open-engine/zeroshot.

The common gap is context. An agent can write the change. It doesn't know which of your repos the change belongs in. Usually a person who knows the system pulls the right repos into a workspace first. In an autonomous factory, nobody does that.

The CodeKB README (awslabs, Apache-2.0, v1.1.0 released 27 November) says it directly: "An autonomous software factory cannot wait for a human to hand-pick repositories for every task."

How it handles that: Tree-sitter parses every function, the call graph is rebuilt, and an LLM on Bedrock describes each function "in business language, together with the code it calls". Titan embeds those descriptions into Amazon S3 Vectors.

The key detail is in the MCP tool's docstring. get_component_from_description accepts space_id, space_ids or hyperspace_id, and you can "omit all to search across every space". So a factory agent can search the whole organisation in one call, then use show_dependencies or trace_flow on the results.

Things to be careful about:

• LLM required: Claude via Amazon Bedrock (default Opus 4.6). Qwen parsing exists but is labelled experimental. Embeddings are fixed to Titan.
• "Local" means the container runs on your machine. It still needs an AWS account, plus S3, S3 Vectors, KMS and a Bedrock Guardrail, created by infra/cli/setup_aws.sh.
• Local mode is single-user with sign-in off. For a team, deploy with CDK. Its default non-dev stages run 10 Fargate tasks of 4 vCPU and 16 GB each.
• Every function costs an LLM call. No benchmarks yet.
• Scheduled refresh and resumable analysis are listed under "Next" on the roadmap.

Read docs/local.md and docs/mcp.md first.

My read: factories are commoditizing fast, so the fight moves underneath them, to whoever owns the map of your codebase. AWS is making that map open source and pinning it to Bedrock.

===== 5. HAMEL HUSAIN STYLE =====

Software factories are the hot thing. Factory, Warp, Coforge and Qodo are all marketing them. There are tutorials (Gauntlet's "How to Build Your Own Software Factory") and open-source versions (superplane, Fabro, addyosmani/factory).

Building the loop is the easy part. What breaks it is context.

Example: a factory agent gets "add gift card payments". At a big company that touches payments, pricing, orders and email, in separate repos. A person who knows the system would pull those into the workspace first. An autonomous agent has no such person, so it guesses or searches. If it misses a repo, every later step builds on that miss.

AWS Labs released CodeKB to fill that step. Here's what it actually gives you, and what it doesn't.

It gives you:

• Business-language descriptions of every function, written by Claude on Bedrock, covering what each function's callees do.
• One MCP search that, with no scope, covers every analyzed repo.
• Call-graph tools (show_dependencies, trace_flow) for impact analysis.
• Refresh that re-summarizes only what changed.

It doesn't give you:

• Model choice. The LLM is Claude via Bedrock and the embeddings are Titan. No OpenAI or local models.
• AWS-free local use. The container runs locally, but it needs your AWS account for Bedrock, S3, S3 Vectors, KMS and a Guardrail.
• Evidence. There are no published benchmarks.
• Unattended ops yet. Scheduled refresh and resumable analysis are on the roadmap.

The summaries are LLM output. A wrong one sends the whole factory to the wrong repo.

Before putting it in a pipeline:

1. Take 30 to 50 closed tickets where you know which repos and functions changed.
2. Run only the retrieval step, with no scope.
3. Score recall of the right repos and call sites against your current method.
4. Track the Bedrock token cost per repo (CodeKB shows it after each analysis).
5. Read every miss and label it: bad summary, bad search, or a link between repos it couldn't see.

Adopt it only if step 3 says it wins.

===== 6. ETHAN MOLLICK STYLE =====

You may have noticed a new phrase: the "software factory".

The idea is a chain of AI agents that takes a request, plans it, writes the code, reviews it and submits it, with little or no human help. Companies are racing to sell it. Factory, Warp, Coforge and Qodo have all launched products or features around it this year. YouTube has full classes on building one, and there are free open-source versions anyone can download.

Building the chain is no longer the hard part. The hard part is that the AI doesn't know your company.

Large organizations split their software into hundreds of separate projects. Something as ordinary as a shopping site's checkout can involve the cart, pricing, payments, orders and email, each in a different project owned by a different team. When a person uses an AI today, someone who knows the system first gathers the right projects and hands them over.

In a true factory there's no one at that step. The AI gets a request and has to work out by itself where the relevant code lives. It's like hiring a very fast contractor and giving them no map of the building.

AWS just released a free, open-source tool called CodeKB that tries to draw that map. It reads every function across all of a company's code and has an AI write a plain-English note about what each one does for the business. The factory's agents can then ask "where do we take payments?" and be pointed to the right places across every project at once.

There are limits. It only works with Anthropic's Claude models, run through Amazon's cloud. You can run the program on your own computer, but it still needs an Amazon cloud account behind it. Every function is read by a paid AI model, so large codebases cost real money. And no one has published evidence yet that it makes the agents' work better.

Still, it points somewhere interesting. If anyone can build the factory, the advantage goes to whoever can write down how their organization actually works.

What happens to the people who carry that knowledge today?
