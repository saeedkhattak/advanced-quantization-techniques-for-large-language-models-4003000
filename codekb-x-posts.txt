===== 1. STORY =====

AWS Open-Sourced A Tool That Tells Your Agent Which Repos A Task Touches

You get a ticket: let customers pay with a gift card.

You open the payments repo, point Claude Code at it, and it writes a clean change. Then the bugs show up. Pricing never subtracts the card. The order service never records it. The receipt email doesn't mention it.

Those lived in other repos. The agent never saw them, because you never pulled them in.

AWS Labs just open-sourced CodeKB to deal with exactly this. It's two weeks old, Apache-2.0, and v1.1.0 shipped on 27 November.

Here's what it does, step by step.

It clones each repo and parses every function and class with Tree-sitter (14 languages, including Python, Java, TypeScript and Go).

Then it rebuilds the call graph, so it knows which function calls which.

Next comes the core idea. A Claude model on Amazon Bedrock writes a short business description of every function, and that description includes what the functions it calls do. So processOrder isn't just "a function". It reads more like "checks stock, charges the card and books shipping".

Those descriptions are embedded and stored as vectors. Now you can search by intent ("where are payments authorized?") and hit code that never uses the word "payment".

From a hit, it walks the graph to show callers and callees. That's your impact analysis.

For users: you can group related repos into a "hyperspace" and search or chat across all of them in a web UI.

For builders: the same tools are exposed over MCP, so Claude Code or Kiro can call get_component_from_description, show_dependencies and trace_flow on their own.

This isn't the first tool in the space. Sourcegraph and Augment both offer cross-repo context over MCP, and DeepWiki writes wikis for public repos. The difference here is the per-function summaries that include callees, and everything runs inside your own AWS account.

A few limits are worth knowing before you get excited.

You need Amazon Bedrock even to run it on your laptop. The default model is Claude Opus 4.6, and every function gets summarized, so a big codebase means a real Bedrock bill. Each space is a snapshot of one branch, capped at 10,000 files. You still choose which repos go into a hyperspace yourself; automatic grouping is only on the roadmap. And there are no published benchmarks yet.

Still, the direction is right. Coding agents rarely fail because they can't write code. They fail because nobody told them where to look.

===== 2. KARPATHY STYLE =====

Spent some time reading the CodeKB README from AWS Labs. The interesting part isn't the search. It's what gets embedded.

The usual move for code RAG is to chunk source files and embed the chunks. That has always felt a bit off to me, because source text is a poor description of what code is for. A function named handle() embeds as roughly nothing.

CodeKB does something different. It parses every function, rebuilds the call graph, and then asks an LLM to write a business-language description of each function, including what its callees accomplish. Those descriptions are what get embedded.

So you're not searching code. You're searching an explanation of code, written bottom-up along the call graph.

The analogy I keep coming back to: it's the difference between searching a book's raw text and searching a good index someone wrote after reading every chapter.

The call graph also helps on updates. When a file changes, it re-summarizes the changed functions and then walks the graph backwards to redo the callers whose descriptions mentioned them. Everything else is reused. That's a clean way to keep the summaries from going stale.

It's exposed over MCP, so an agent like Claude Code can search by intent and then follow callers and callees across repos you've grouped together.

The costs are real though. It needs Amazon Bedrock even locally, and every function gets an LLM pass (default model Claude Opus 4.6). It's a two-week-old repo with no published benchmarks.

What I'd actually want to see: the same task set run by an agent with and without this, measuring whether it finds the repos and call sites a human would have. That's the number that matters.

===== 3. SIMON WILLISON STYLE =====

CodeKB, new from AWS Labs (Apache-2.0, v1.1.0 released 27 November 2026).

The README pitch: "Not code indexing. Code understanding."

What it is: a single container that serves a web UI, a REST API and an MCP server. You give it Git URLs. It parses the code with Tree-sitter, rebuilds the call graph, and then has an LLM on Amazon Bedrock describe each function "in business language, together with the code it calls". Those descriptions are embedded with Titan into Amazon S3 Vectors.

Two things I found genuinely interesting.

First, the descriptions include the callees. A function's summary says what it achieves through the code it calls, which makes intent search ("where are payments authorized?") work much better than embedding raw source.

Second, incremental refresh. Changed files are re-parsed, then it "walks the call graph in reverse to find the callers whose descriptions included the changed code" and re-summarizes only those.

The MCP tools are the part coding agents will use: get_component_from_description, show_dependencies (with incoming dependents for impact analysis), trace_flow and get_call_graph_with_source. The README shows Kiro and Claude Code as clients.

Things to be careful about:

• It needs Amazon Bedrock even when run locally. The default model is Claude Opus 4.6.
• Cost is mostly Bedrock summarization, and it scales with the number of functions.
• The CDK deployment's default non-dev stages run 10 Fargate tasks of 4 vCPU and 16 GB each. Check that before you deploy.
• A space is one branch at one commit, capped at 10,000 source files.
• The README says it "automatically and reliably selects the relevant repositories". In this version you group repos into hyperspaces yourself; automatic grouping is listed under "Later" on the roadmap.
• No benchmarks yet. Benchmarking is listed under "Next".

The docs folder is well written. Start with mcp.md and faq.md.

===== 4. SWYX STYLE =====

Context engines for coding agents are becoming their own product category, and AWS just put an open-source entry into it.

CodeKB (awslabs, Apache-2.0) indexes your repos and serves the results to agents over MCP.

Where everyone else sits right now:

• Sourcegraph: cross-repo search and precise code navigation, exposed over MCP.
• Augment Context Engine: its retrieval layer shipped as a standalone MCP server in February 2026.
• DeepWiki: generated wikis and Q&A for public GitHub repos.
• Greptile: a code graph, aimed mostly at AI code review.
• AWS's own earlier Git Repo Research MCP server: semantic search over a repo, now deprecated.

CodeKB's angle is the index itself. It parses every function, rebuilds the call graph, and has Claude on Bedrock write a business description of each function that covers what its callees do. You search those descriptions by intent, then walk callers and callees for impact analysis. Related repos group into "hyperspaces" so one query spans a whole system.

It's also fully self-hosted in your AWS account, which is the selling point for enterprises that won't send code to a startup's cloud.

The tradeoffs: Bedrock is required even locally, every function costs an LLM call, the repo is two weeks old, and there are no published benchmarks.

My read on where this goes: the model is getting commoditized, so the fight moves to who owns the map of your codebase. Expect every cloud and every coding-agent vendor to ship one of these, and expect the open ones to compete on refresh cost and benchmark numbers.

===== 5. HAMEL HUSAIN STYLE =====

AWS Labs released CodeKB, a cross-repo "code understanding" service for coding agents. Before you wire it into anything, separate what it gives you from what it doesn't.

What it gives you:

• A business-language description of every function, written by a Claude model on Bedrock, including what its callees do.
• Semantic search over those descriptions, so you can find code by intent.
• Call-graph tools over MCP (get_component_from_description, show_dependencies, trace_flow) that Claude Code or Kiro can call.
• Incremental refresh that only re-summarizes changed functions and their callers.

What it doesn't give you:

• Any evidence it helps. There are no published benchmarks; benchmarking is on the roadmap under "Next".
• Automatic repo selection across the whole org. You group repos into hyperspaces yourself in this version.
• A cheap run. Every function gets an LLM call, and Bedrock is required even locally.
• History. A space is one branch at one commit.

The summaries are LLM output, which means they can be wrong, and a wrong summary sends your agent to the wrong place with full confidence. That's the failure mode to look for.

If you want to know whether it's worth it for your codebase, do this:

1. Write down 20 to 30 real past tasks where you know which repos and functions were touched.
2. Run your agent on them without CodeKB and record what it found and missed.
3. Run it again with the CodeKB MCP tools connected.
4. Compare recall of the right repos and call sites, plus the Bedrock token cost per space (CodeKB shows it after each analysis).
5. Read the traces where it got it wrong, and check whether the bad summary or the search was at fault.

Then decide.

===== 6. ETHAN MOLLICK STYLE =====

When an AI agent changes code at a big company, how does it know what else it might break?

Mostly, it doesn't. Large software is split into many separate projects, often hundreds, each owned by a different team. One feature, like checkout on a shopping site, can be spread across the cart, pricing, payments, orders and email. The knowledge of how they connect usually sits in a few senior engineers' heads.

So today a person picks which projects to show the AI, and hopes they didn't forget one.

AWS Labs just released a free, open-source tool called CodeKB that tries to write that knowledge down. It reads every function in your code and has an AI write a plain-English note about what it does for the business, including what it gets done through the other code it calls.

Think of it as the difference between a library with books on shelves and a library where someone has written an accurate summary card for every book. You can now ask "where do we take payments?" and get pointed to the right place, even if the code never uses that word. The AI coding assistant can ask the same question.

There are good reasons for caution. Nobody has published evidence yet that it improves the agents' work. The summaries are themselves AI-written, so they can be wrong. And it costs money to run, since every function gets read by a paid model on Amazon's cloud.

What we do know is that the bottleneck has shifted. The models can write the code. The hard part is knowing your organization well enough to know where the code goes.

Which raises the question: if an AI can write down the knowledge your senior engineers carry around, what happens to how companies value that knowledge?
