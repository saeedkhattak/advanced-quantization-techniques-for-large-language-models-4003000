===== 1. STORY =====

𝗔𝗻 𝗔𝗜 𝗧𝗲𝗮𝗺 𝗧𝗵𝗮𝘁 𝗪𝗼𝗿𝗸𝘀 𝗧𝗵𝗿𝗼𝘂𝗴𝗵 𝗬𝗼𝘂𝗿 𝗚𝗶𝘁𝗛𝘂𝗯 𝗜𝘀𝘀𝘂𝗲𝘀

Most repos have a pile of small open issues. A wrong label on a button, a missing check on a form, a date in the wrong format. Nobody gets to them, so they sit there for months.

ZazenCodes published a setup that hands that pile to a team of Claude Code agents. The project calls it a software factory. 𝗜𝘁'𝘀 𝗳𝗿𝗲𝗲 𝗼𝗻 𝗚𝗶𝘁𝗛𝘂𝗯 𝗮𝗻𝗱 𝗵𝗮𝘀 𝟱𝟯𝟬 𝘀𝘁𝗮𝗿𝘀 𝗮𝘀 𝗼𝗳 𝘁𝗼𝗱𝗮𝘆.

One issue goes through it like this.

You write the issue and add the label 𝚏𝚊𝚌𝚝𝚘𝚛𝚢. Then you type /𝚏𝚊𝚌𝚝𝚘𝚛𝚢 𝚛𝚞𝚗 in Claude Code.

An intake agent reads it first. It can reject it, cut it down to something smaller, or ask the author a question and wait for the answer.

A spec writer turns the issue into a spec. A builder writes the code on its own branch and opens a draft PR that says "Closes #n".

Then a plain script runs your own tests, lint and build. 𝗜𝗳 𝘁𝗵𝗲 𝗰𝗵𝗲𝗰𝗸𝘀 𝗳𝗮𝗶𝗹, 𝗻𝗼 𝗿𝗲𝘃𝗶𝗲𝘄𝗲𝗿 𝗲𝘃𝗲𝗿 𝘀𝗲𝗲𝘀 𝘁𝗵𝗲 𝗰𝗼𝗱𝗲. It goes back to the builder with the error log.

Reviewers only read the diff after that. The code reviewer runs every time. UX and UI reviewers join when the change touches the screen, and a security reviewer joins when intake flags a risk.

Last, an approver either merges the PR or tags the issue 𝚏𝚊𝚌𝚝𝚘𝚛𝚢:𝚗𝚎𝚎𝚍𝚜-𝚑𝚞𝚖𝚊𝚗 and leaves it for you.

𝗜𝗳 𝘆𝗼𝘂 𝗷𝘂𝘀𝘁 𝘄𝗮𝗻𝘁 𝘁𝗼 𝘂𝘀𝗲 𝗶𝘁: it runs on your own machine inside a Claude Code session, not in CI. It works on 𝘂𝗽 𝘁𝗼 𝟯 𝗶𝘀𝘀𝘂𝗲𝘀 𝗮𝘁 𝗼𝗻𝗰𝗲 by default. If the session dies, /𝚏𝚊𝚌𝚝𝚘𝚛𝚢 𝚛𝚞𝚗 carries on from where it stopped, because every job's state is saved in files.

𝗜𝗳 𝘆𝗼𝘂 𝗯𝘂𝗶𝗹𝗱 𝘁𝗵𝗶𝗻𝗴𝘀 𝗹𝗶𝗸𝗲 𝘁𝗵𝗶𝘀: the v2 design is 𝟴 𝗮𝗴𝗲𝗻𝘁𝘀, 𝟯 𝘀𝗰𝗿𝗶𝗽𝘁𝘀 𝗮𝗻𝗱 𝗼𝗻𝗲 𝗰𝗼𝗻𝗳𝗶𝗴 𝗳𝗶𝗹𝗲. The agents are just Markdown files. Low-risk changes get a cheap Haiku reviewer, while Opus writes the spec, the code and the final call. One small detail stands out: the gate runs the main branch's copy of 𝚌𝚑𝚎𝚌𝚔𝚜.𝚜𝚑, so a branch can't quietly edit the checks it's judged by.

Issue-to-PR agents aren't new. GitHub's Copilot coding agent opens a draft PR when you assign it an issue. Claude Code's own GitHub Action does the same from an @claude comment, and OpenHands has a fix-me label. Those mostly hand the whole job to one agent. This one splits it into roles, with a script checking the work in the middle.

𝗢𝗻𝗲 𝗰𝗮𝘃𝗲𝗮𝘁: 𝘁𝗵𝗲 𝗼𝗻𝗹𝘆 𝗽𝘂𝗯𝗹𝗶𝘀𝗵𝗲𝗱 𝗿𝘂𝗻𝘀 𝗮𝗿𝗲 𝗼𝗻 𝗮 𝘀𝗺𝗮𝗹𝗹 𝗰𝗮𝗹𝗰𝘂𝗹𝗮𝘁𝗼𝗿 𝗿𝗲𝗽𝗼, with Haiku playing every role. Two jobs merged, one was rejected at intake, and one went to a human after three rounds. It also spends your Claude plan and, in v2, can merge real PRs by itself, so the README says start with one job at a time and read every PR.

The repo is really the companion code for the Season 3 YouTube videos on that channel. The factory folders are what people are starring.

===== 2. KARPATHY STYLE =====

𝗧𝗵𝗲 𝗦𝗼𝗳𝘁𝘄𝗮𝗿𝗲 𝗙𝗮𝗰𝘁𝗼𝗿𝘆 𝗜𝘀 𝗠𝗼𝘀𝘁𝗹𝘆 𝗮 𝗦𝘁𝗮𝘁𝗲 𝗠𝗮𝗰𝗵𝗶𝗻𝗲

The ZazenCodes software factory is trending on GitHub (530 stars as of today). It turns labeled GitHub issues into reviewed PRs using a team of Claude Code agents.

The agents are the part everyone screenshots. 𝗧𝗵𝗲 𝗶𝗻𝘁𝗲𝗿𝗲𝘀𝘁𝗶𝗻𝗴 𝗽𝗮𝗿𝘁 𝗶𝘀 𝘁𝗵𝗲 𝗰𝗼𝗱𝗲 𝗮𝗿𝗼𝘂𝗻𝗱 𝘁𝗵𝗲𝗺.

The design doc puts it in one line: "𝘚𝘤𝘳𝘪𝘱𝘵𝘴 𝘥𝘦𝘤𝘪𝘥𝘦 𝘸𝘩𝘦𝘵𝘩𝘦𝘳 𝘪𝘵 𝘸𝘰𝘳𝘬𝘴." Agents decide whether it's good.

So the test run is not an agent's opinion. A script runs your 𝚌𝚑𝚎𝚌𝚔𝚜.𝚜𝚑 before any reviewer is spawned, and runs it again after syncing with main, right before merge. A broken build goes back to the builder and never reaches review.

Then every job is a small state machine. 𝚓𝚘𝚋.𝚓𝚜𝚘𝚗 has 𝟭𝟭 𝗽𝗼𝘀𝘀𝗶𝗯𝗹𝗲 𝘀𝘁𝗮𝗴𝗲𝘀, from intake to merged or rejected. Only one script is allowed to write that file, and it refuses moves that aren't in its transition table. Since state is files, a crashed session just resumes.

I think of it like a kitchen. The chef can taste and judge, but the oven thermometer isn't the chef's opinion, and nobody lets the chef repaint the thermometer. Here the gate even uses the main branch's copy of 𝚌𝚑𝚎𝚌𝚔𝚜.𝚜𝚑, so the branch being judged can't edit its own test.

imo this is the right split. Put LLMs where you need judgment (is this issue worth doing, is this diff any good) and plain code everywhere you need a fact.

What's missing is data. The published example runs are 𝟰 𝗷𝗼𝗯𝘀 𝗼𝗻 𝗮 𝘁𝗼𝘆 𝗰𝗮𝗹𝗰𝘂𝗹𝗮𝘁𝗼𝗿 𝗿𝗲𝗽𝗼, all on Haiku. Two merged, one was rejected, one escalated.

It also routes by risk. A low-risk change with no UI gets one Haiku reviewer. Medium and high risk get Sonnet. Security flags pull in an Opus reviewer. All of that lives in one config file.

This repo is useful because it makes all of those choices visible and editable in files you own.

• 𝗥𝗲𝗮𝗱𝗮𝗯𝗹𝗲 𝘁𝗿𝗮𝗰𝗲𝘀: every stage writes a file, and each file opens with a short summary. A job folder is a full record of what each agent decided.

• 𝗖𝗼𝘀𝘁 𝗽𝗲𝗿 𝗷𝗼𝗯: shown on a local dashboard, though it's an API-equivalent estimate, not your bill.

What it doesn't give you:

• 𝗔𝗻𝘆 𝗺𝗲𝗮𝘀𝘂𝗿𝗲 𝗼𝗳 𝗾𝘂𝗮𝗹𝗶𝘁𝘆 𝗼𝗻 𝗮 𝗿𝗲𝗮𝗹 𝗰𝗼𝗱𝗲𝗯𝗮𝘀𝗲. The published examples are 𝟰 𝗷𝗼𝗯𝘀 𝗼𝗻 𝗮 𝘀𝗺𝗮𝗹𝗹 𝗰𝗮𝗹𝗰𝘂𝗹𝗮𝘁𝗼𝗿 𝗿𝗲𝗽𝗼, all agents on Haiku. 2 merged, 1 rejected at intake, 1 escalated after three rounds.

• 𝗔 𝘄𝗮𝘆 𝘁𝗼 𝗸𝗻𝗼𝘄 𝗶𝗳 𝘁𝗵𝗲 𝗿𝗲𝘃𝗶𝗲𝘄𝗲𝗿𝘀 𝗮𝗿𝗲 𝗮𝗻𝘆 𝗴𝗼𝗼𝗱. An LLM reviewer passing a diff tells you the reviewer passed it. Nothing more.

So if you're thinking about using it, test it on your own repo first:

• 𝗦𝘁𝗲𝗽 𝟭: pick 20 issues you've already closed, where you know what a good fix looks like.

• 𝗦𝘁𝗲𝗽 𝟮: baseline. Solve each one with a single plain Claude Code session.

• 𝗦𝘁𝗲𝗽 𝟯: run the factory on the same 20 with concurrency set to 1.

• 𝗦𝘁𝗲𝗽 𝟱: read the job folders. Every spec, every review. That's where you'll see whether intake and the reviewers are catching real problems.

===== 6. ETHAN MOLLICK STYLE =====

𝗪𝗵𝗮𝘁 𝗛𝗮𝗽𝗽𝗲𝗻𝘀 𝗪𝗵𝗲𝗻 𝗔𝗜 𝗪𝗿𝗶𝘁𝗲𝘀 𝘁𝗵𝗲 𝗖𝗼𝗱𝗲 𝗮𝗻𝗱 𝗔𝗜 𝗥𝗲𝘃𝗶𝗲𝘄𝘀 𝗜𝘁?

A small open-source project is trending on GitHub this week, and it raises a bigger question about how software gets made.

Some background for non-coders. On GitHub, an 𝘪𝘴𝘴𝘶𝘦 is a request: "add a dark mode" or "this button is broken". A 𝘱𝘶𝘭𝘭 𝘳𝘦𝘲𝘶𝘦𝘴𝘵 is the finished code someone hands in, which a colleague reviews before it's merged.

Normally people do both the writing and the reviewing. The ZazenCodes "software factory" gives both jobs to AI.

𝗧𝗵𝗶𝗻𝗸 𝗼𝗳 𝗮 𝘀𝗺𝗮𝗹𝗹 𝗻𝗲𝘄𝘀𝗿𝗼𝗼𝗺. One AI decides whether the story is worth running. Another writes the brief. Another writes the piece. A strict, non-AI fact check runs the project's own tests, and anything that fails goes straight back. Then AI editors review it, and a final AI editor either publishes it or sends it to a human.

The case for it is real. Splitting work into roles means no single AI marks its own homework. The automatic tests catch broken code before any AI reviewer sees it. And a cheap model can handle low-risk changes, which keeps cost down.

The case for caution is real too. The only published results are 𝗳𝗼𝘂𝗿 𝘁𝗲𝘀𝘁 𝗷𝗼𝗯𝘀 𝗼𝗻 𝗮 𝘁𝗶𝗻𝘆 𝗰𝗮𝗹𝗰𝘂𝗹𝗮𝘁𝗼𝗿 𝗮𝗽𝗽. We don't know yet how it does on large, messy software. AI reviewers may share blind spots with the AI that wrote the code, and nobody has measured that here. And the newest version can merge code with no human sign-off when it feels confident.

What we do know: it's free, it's open source, and 𝟱𝟯𝟬 𝗽𝗲𝗼𝗽𝗹𝗲 𝗵𝗮𝘃𝗲 𝘀𝘁𝗮𝗿𝗿𝗲𝗱 𝗶𝘁 𝗮𝘀 𝗼𝗳 𝘁𝗼𝗱𝗮𝘆. The author's own advice is to start with one job at a time and review every pull request.
