===== 1. STORY =====

𝗔𝗪𝗦 𝗝𝘂𝘀𝘁 𝗣𝘂𝘁 𝗮 𝗖𝗼𝗽𝘆 𝗼𝗳 𝗜𝘁𝘀 𝗖𝗹𝗼𝘂𝗱 𝗼𝗻 𝗬𝗼𝘂𝗿 𝗟𝗮𝗽𝘁𝗼𝗽

You write code that talks to S3 or DynamoDB. To test it, you either deploy to a real account and pay, or you lean on a mock that may not behave like AWS at all.

AWS's answer, released on 11 November: 𝗔𝗪𝗦 𝗘𝗺𝘂𝗹𝗮𝘁𝗼𝗿.

It runs on your machine and answers the same API calls AWS does. You point the AWS CLI or an SDK at it with environment variables, and your code doesn't know the difference. It doesn't need an AWS account, and 𝘁𝗵𝗲𝗿𝗲'𝘀 𝗻𝗼 𝗲𝘅𝘁𝗿𝗮 𝘀𝗲𝗿𝘃𝗶𝗰𝗲 𝗳𝗲𝗲.

There are three ways to run it:

• 𝗦𝗲𝗿𝘃𝗲𝗿 𝗺𝗼𝗱𝗲: an RPM or Debian package on Linux, Docker on Mac and Windows
• 𝗘𝗺𝗯𝗲𝗱𝗱𝗲𝗱 𝗺𝗼𝗱𝗲: inside Rust tests, one isolated emulator per test
• 𝗔𝗴𝗲𝗻𝘁 𝘀𝗸𝗶𝗹𝗹: a coding agent installs it through the AWS CLI (2.35.0 or later)

The part people are talking about is how it was made. AWS says 𝗮𝘂𝘁𝗼𝗻𝗼𝗺𝗼𝘂𝘀 𝗔𝗜 𝗮𝗴𝗲𝗻𝘁𝘀 𝘄𝗿𝗼𝘁𝗲 𝗶𝘁, and its own engineering post says no human wrote or reviewed the code. Build checks and other agents do the reviewing. The repo has 𝟮𝟵,𝟲𝟴𝟰 𝗰𝗼𝗺𝗺𝗶𝘁𝘀 on main and it doesn't accept pull requests.

For users, this means cheap, fast integration tests and a sandbox a coding agent can't break.

For builders, it means the code is CC0 (public domain), with one crate per AWS service, each generated from a Smithy model.

It isn't the first tool of its kind. LocalStack has done this for years, Moto mocks AWS in Python, and Floci and MiniStack are newer free options. What's new is that AWS itself ships one, and that it's this wide (reports say 𝟮𝟬𝟬+ 𝘀𝗲𝗿𝘃𝗶𝗰𝗲𝘀).

One caveat: coverage is far from complete. The repo's own issues folder holds 𝗺𝗼𝗿𝗲 𝘁𝗵𝗮𝗻 𝟲,𝟬𝟬𝟬 𝗻𝗼𝘁𝗲𝘀 𝗼𝗻 𝘁𝗵𝗶𝗻𝗴𝘀 𝘁𝗵𝗮𝘁 𝗱𝗼𝗻'𝘁 𝘄𝗼𝗿𝗸 𝘆𝗲𝘁. Unsupported calls reportedly return a 501. Telemetry is 𝗼𝗻 𝗯𝘆 𝗱𝗲𝗳𝗮𝘂𝗹𝘁 (you can switch it off). Building from source needs 𝗮𝗯𝗼𝘂𝘁 𝟭𝟬𝟬 𝗚𝗕 𝗼𝗳 𝗱𝗶𝘀𝗸.

===== 2. KARPATHY STYLE =====

𝗧𝗵𝗲 𝗜𝗻𝘁𝗲𝗿𝗲𝘀𝘁𝗶𝗻𝗴 𝗣𝗮𝗿𝘁 𝗼𝗳 𝗔𝗪𝗦 𝗘𝗺𝘂𝗹𝗮𝘁𝗼𝗿 𝗜𝘀𝗻'𝘁 𝘁𝗵𝗲 𝗘𝗺𝘂𝗹𝗮𝘁𝗼𝗿

AWS shipped a local emulator of its APIs on 11 November. It's free and needs no account. It runs as a server, in Docker or inside Rust tests.

Local AWS emulators aren't new. LocalStack and Moto have been around for years.

𝗧𝗵𝗲 𝗶𝗻𝘁𝗲𝗿𝗲𝘀𝘁𝗶𝗻𝗴 𝗽𝗮𝗿𝘁 𝗶𝘀 𝗵𝗼𝘄 𝗶𝘁 𝗴𝗼𝘁 𝗯𝘂𝗶𝗹𝘁. AWS says autonomous agents wrote the code, and that no human wrote or reviewed it. There are 𝟮𝟵,𝟲𝟴𝟰 𝗰𝗼𝗺𝗺𝗶𝘁𝘀 on main.

I think this is the right kind of problem to hand to agents. An emulator has a spec you can test against: the real AWS. You send the same request to both and compare the responses. That gives you a loop with a clear "correct", which is what agents need most.

AWS publishes a fidelity score per service with each release, based on how many tests pass. That's the honest metric here, more than any count of services.

The weak spot is the long tail. The repo tracks 𝗺𝗼𝗿𝗲 𝘁𝗵𝗮𝗻 𝟲,𝟬𝟬𝟬 𝗻𝗼𝘁𝗲𝘀 𝗼𝗻 𝘁𝗵𝗶𝗻𝗴𝘀 𝘁𝗵𝗮𝘁 𝗱𝗼𝗻'𝘁 𝘄𝗼𝗿𝗸 𝘆𝗲𝘁, sitting next to more than 12,000 that were fixed. That's what agent-built software looks like imo: very wide, mostly right, and with gaps you only find by running it.

𝘞𝘩𝘢𝘵 𝘐'𝘥 𝘢𝘤𝘵𝘶𝘢𝘭𝘭𝘺 𝘸𝘢𝘯𝘵 𝘵𝘰 𝘴𝘦𝘦 𝘪𝘴 𝘵𝘩𝘦 𝘧𝘪𝘥𝘦𝘭𝘪𝘵𝘺 𝘤𝘶𝘳𝘷𝘦 𝘰𝘷𝘦𝘳 𝘵𝘪𝘮𝘦. 𝘋𝘰𝘦𝘴 𝘵𝘩𝘦 𝘨𝘢𝘱 𝘴𝘩𝘳𝘪𝘯𝘬, 𝘰𝘳 𝘭𝘦𝘷𝘦𝘭 𝘰𝘧𝘧?

===== 4. SWYX STYLE =====

• 𝗟𝗼𝗰𝗮𝗹𝗦𝘁𝗮𝗰𝗸: the default for a long time. Its packaging changed in March 2026, and the free Hobby tier is for non-commercial use only.

• 𝗙𝗹𝗼𝗰𝗶, 𝗠𝗶𝗻𝗶𝗦𝘁𝗮𝗰𝗸: free MIT projects pitched as LocalStack replacements.

Now AWS has shipped its own. 𝗔𝗪𝗦 𝗘𝗺𝘂𝗹𝗮𝘁𝗼𝗿 came out on 11 November. It's CC0, free, and reports put it at 𝟮𝟬𝟬+ 𝘀𝗲𝗿𝘃𝗶𝗰𝗲𝘀.

It fits as the "official" option, and the vendor owns the ground truth. Fidelity is measured against real AWS and published with each release.

===== 5. HAMEL HUSAIN STYLE =====

𝗕𝗲𝗳𝗼𝗿𝗲 𝗬𝗼𝘂 𝗦𝘄𝗮𝗽 𝗬𝗼𝘂𝗿 𝗧𝗲𝘀𝘁 𝗦𝗲𝘁𝘂𝗽 𝗳𝗼𝗿 𝗔𝗪𝗦 𝗘𝗺𝘂𝗹𝗮𝘁𝗼𝗿

AWS Emulator (released 11 November) runs the AWS APIs locally, free, with no account. AWS says agents wrote it.

What it gives you:

• 𝗧𝗵𝗲 𝗿𝗲𝗮𝗹 𝗦𝗗𝗞 𝗮𝗻𝗱 𝗖𝗟𝗜 pointed at a local endpoint

• 𝗔 𝘀𝗮𝗻𝗱𝗯𝗼𝘅 𝗳𝗼𝗿 𝗰𝗼𝗱𝗶𝗻𝗴 𝗮𝗴𝗲𝗻𝘁𝘀 that can't touch your real account
• 𝗣𝘂𝗯𝗹𝗶𝘀𝗵𝗲𝗱 𝗳𝗶𝗱𝗲𝗹𝗶𝘁𝘆 𝘀𝗰𝗼𝗿𝗲𝘀 per service, with each release

What it doesn't give you:

• 𝗙𝘂𝗹𝗹 𝗰𝗼𝘃𝗲𝗿𝗮𝗴𝗲. The repo tracks 𝗺𝗼𝗿𝗲 𝘁𝗵𝗮𝗻 𝟲,𝟬𝟬𝟬 𝗸𝗻𝗼𝘄𝗻 𝗴𝗮𝗽𝘀. Unsupported calls reportedly return 501.
• 𝗣𝗿𝗼𝗼𝗳 𝗶𝘁 𝗺𝗮𝘁𝗰𝗵𝗲𝘀 𝘆𝗼𝘂𝗿 𝘂𝘀𝗲. A high service-wide score says nothing about the five calls your app depends on.
• 𝗣𝗿𝗶𝘃𝗮𝗰𝘆 𝗯𝘆 𝗱𝗲𝗳𝗮𝘂𝗹𝘁. Telemetry is on until you turn it off.

If you're thinking of switching, here's how I'd test it:

1. List the AWS calls your app actually makes, with real request shapes.
2. Run your integration tests against real AWS once and save the results as a baseline.
3. Run the same tests against the emulator and diff the responses, errors included.
4. Read the failures one by one, and check them against 𝚒𝚜𝚜𝚞𝚎𝚜/𝚝𝚑𝚒𝚗𝚐𝚜-𝚝𝚑𝚊𝚝-𝚍𝚘-𝚗𝚘𝚝-𝚠𝚘𝚛𝚔/.
5. Pin a release, and run this again each time you upgrade.

There's evidence on both sides.

What we actually know is narrow. Agents can produce very wide, testable software that a big company is willing to put its name on. We don't yet know how it holds up after months of real use.
